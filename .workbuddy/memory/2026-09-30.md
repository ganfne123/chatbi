## 改用 json_schema 约束 LLM 输出（同日）

对着本项目端点（DashScope 兼容模式 / qwen3.7-plus）实测了 4 种结构化输出方式：

| 方式 | 结果 |
|---|---|
| `response_format={"type":"json_object"}` | 支持，但只保证合法 JSON，字段照样乱编（多出 chinese_name 等） |
| `response_format={"type":"json_schema","strict":True,...}` | **支持，推荐**：字段、类型、enum 全约束住 |
| `tools` + `tool_choice` 强制调用 | **不支持**：thinking 模式下报 `tool_choice parameter does not support being set to required or object` |
| `client.beta.chat.completions.parse(response_format=BaseModel)` | 支持，但普通 `str` 字段无 enum 约束，要约束得用 `Literal[...]` |

结论已落地到 `join_resolver.py`：加 `INTENT_SCHEMA`（`table_type` 用 enum 锁三个值、
`additionalProperties: False`、三字段全 required），请求带 `response_format=INTENT_SCHEMA`。
由此可以**删掉**之前防御性的 ```json 剥离正则和 `TYPE_ALIASES` 别名表 —— 结构上不会再歪。
换模型供应商时若不支持 json_schema，降级顺序：json_schema → pydantic Literal + parse
→ json_object → 手动解析。
